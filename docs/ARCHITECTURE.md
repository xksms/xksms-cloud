# xksms-cloud 架构演进蓝图

本文档梳理 xksms-cloud 在构建企业级 SaaS 平台过程中经历的四个关键演进阶段，作为团队对齐架构理念与落地路径的参考。

## 阶段一：奠定基石 —— 认证与用户管理的彻底解耦

* **职责单一**：`xksms-auth` 聚焦 OAuth2/OIDC 协议实现与令牌签发，保持无状态，所有用户数据均来自 `xksms-user`。
* **安全隔离**：`xksms-user` 封装密码哈希、资料与权限，向外只暴露标准 `Result<UserAuthDTO>`，敏感字段从未离开用户中心的安全域。
* **扩展弹性**：认证流程无需了解数据存储细节即可扩展短信、扫码、企微等登录方式，真正做到“协议层扩展、数据层稳定”。

## 阶段二：确立边界 —— API 与 Biz 契约化

* **模块结构**：所有服务遵循 `*-api`（契约层） + `*-biz`（实现层）双模块模式。调用方仅依赖 `api` 即可完成编译。
* **契约优先**：先设计 DTO 与 Feign 接口，再实现业务逻辑，避免随意暴露内部模型造成的强耦合。
* **依赖防腐**：Biz 模块不被其他服务直接引用，从物理层阻断了循环依赖与跨域侵入。

## 阶段三：架构升维 —— 多租户 SaaS 数据模型

* **租户优先**：`sys_tenant` 作为资源归属的根节点，所有业务实体均携带 `tenant_id`。
* **权责拆分**：账号（`sys_user_account`）、资料（`sys_user_profile`）、权限（RBAC 表）按安全等级拆分，配套乐观锁与审计字段。
* **版本治理**：所有结构调整通过 Flyway 脚本提交，与代码同源管理，保障多环境一致性。

## 阶段四：领域驱动 —— 目录即架构

* **平台层 (`xksms-platform`)**：沉淀认证、用户、系统、通知等基础能力，供所有业务服务复用。
* **业务层 (`xksms-modules`)**：承载订单、产品等领域服务，严格依赖平台能力但不会被平台反向依赖。
* **团队协同**：目录划分即团队边界，平台团队负责平台层，业务团队负责领域层，避免职责漂移。

> 以上阶段不是一次性完成，而是持续演进的结果。任何新增模块都应评估其所处阶段，确保不破坏既有的架构边界。
